# M2 失败轨迹标注指南（给标注人）

预计用时：**2–3 小时**（建议分两段，每段 50 条）。不需要编程背景。

## 一、背景（30 秒版）

大语言模型（LLM）智能体是让 AI 自动完成软件工程任务的工具：给它一句「修复某开源项目的 bug」，它会自己一步步执行终端命令——查看目录、改文件、跑测试、根据测试结果再改，如此往复。这些「一步步」的操作记录下来就是一条**轨迹**（trajectory）。

我们的研究想回答：**这些智能体失败的时候，有没有什么反复出现的固定套路？** 为了验证计算机自动挖出的套路像不像人眼中的失败原因，需要真人先独立标注一批失败轨迹作为参照——这就是你的工作。

## 二、你看的材料

`booklet.md`：100 条失败轨迹。每条轨迹是一串 `动作:结果` 记号，按步排列，例如：

```
ls:ok  cd:ok  pytest:err  pytest:err  sed:ok  pytest:ok  git:ok
```

含义：`ls:ok` = 执行了 ls 命令且成功；`pytest:err` = 跑了测试但失败。`other:err` = 某种不常见的命令执行出错。**只看这个序列就够了，不需要读懂每条命令的细节**——就像看「棋谱」而不是「棋理」。

## 三、每条轨迹填三栏

| 栏 | 内容 | 说明 |
|---|---|---|
| ① 失败原因 | 自由文本，一句话 | 你认为这条轨迹为什么最终失败。用你自己的话写，**不要**从给定清单里选（没有清单）。可以写得朴素，如「测试一直红，改不动了」「似乎在原地打转」「执行了无效命令后放弃」。 |
| ② 关键步骤区间 | 如 `12–18`，可空 | 哪几步最能体现你判断的失败原因。 |
| ③ 置信度 | 高 / 中 / 低 | 「高」= 看完很确定；「低」= 只是猜测。拿不准就写低，**这很有价值，不算失败**。 |

## 四、三条判例（先看这个再开工）

**例 1**（无效动作后放弃）：
```
grep:ok grep:err grep:err other:err cd:ok exit:ok
```
→ ① 反复执行出错命令后放弃，未做有效修改 ② 2–4 ③ 高

**例 2**（测试一直红）：
```
sed:ok pytest:err sed:ok pytest:err sed:ok pytest:err pytest:err exit:ok
```
→ ① 反复修改但测试始终失败，耗尽尝试 ② 1–7 ③ 高

**例 3**（循环打转）：
```
cd:ok ls:ok cd:ok ls:ok cd:ok ls:ok cd:ok ls:ok exit:ok
```
→ ① 在目录间来回切换，没有实质进展 ② 1–8 ③ 中

## 五、规则

1. **独立完成**：不要和另一位标注人讨论，不要上网查这条轨迹的「标准答案」。两人独立标注正是实验设计的一部分。
2. **按顺序标**：建议一次标完 50 条再休息，避免疲劳影响质量。
3. **每 20 条自查一次**：你的①是否都是「为什么会失败」而不是「做了什么」。
4. **写不出就写低置信度 + 最佳猜测**，不要留空。
